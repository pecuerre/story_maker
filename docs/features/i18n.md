# Translations

[ADR 0016](../adr/0016-internationalization-and-browser-locale.md) decides why the language is a
browser-owned preference and which strings are excluded. The Settings page that chooses it is in
[features/settings.md](settings.md); how the locale reaches a request is in
[architecture.md](../architecture.md#request-lifecycle).

Application chrome is written behind `t("dotted.key")` and lives in `config/locales/en.yml` (the
source of truth) with a Spanish `config/locales/es.yml` mirroring it. These are the rules a new
string has to follow.

## Naming and structure

- **Group keys by the surface that owns the string** — `layouts.*`, `sidebar.*`, `shared.*`,
  `settings.*`, `sessions.*`, `passwords.*`, and then the workspace that owns them — rather than
  adding to a flat list.
- **A key is added to both files in the same change.** `config.i18n.raise_on_missing_translations` is
  on in the test environment and `test/models/translations_test.rb` compares the two key sets, so a
  one-sided key fails the suite.
- **Author-entered data is never translated.** Record names, descriptions, tag names, and universe and
  story names are the author's words. They are not keys and must not become keys.
- **Interpolate with named arguments** (`t("shared.record_photo.alt", name: record.name)`) so a
  translation can reorder the sentence. Positional `%1`/`%2` is not used.
- **Never name an interpolation `locale`, `default`, `scope`, or `raise`.** They are reserved I18n
  options, not interpolation variables: `t(key, locale: "Español")` asks I18n to translate *in* a
  locale called Español and raises `I18n::InvalidLocale`. `count` is only a pluralization input.
  `TranslationsTest` fails the suite if one appears.
- **Pluralize with `count:`** and give the key `one:`/`other:` forms. A count is never assembled by
  appending an "s".
- **A count label is a key, not a noun.** A workspace passes `count_label: "character"`, and
  `ApplicationHelper#count_with_label` resolves it with a `count:` so the locale chooses the plural.
  Those record-type nouns therefore live at the **root** of the locale files.
- **A value that travels in a URL is not translated.** `SceneFilter::UNGROUPED` and a search scope's
  `value` are query values; only the label beside them is translated. `SectionPaths::UNGROUPED_LABEL_KEY`
  and `SceneFilter::UNGROUPED` are the same shape, and `sections.ungrouped_label` is the one label the
  Scenes list badge, the Scene editor's Section selector, the Scenes filter, and the Sections
  workspace's ungrouped block all read, so the four surfaces cannot disagree about the word.
- **A record type that a tab opens is named by that workspace.** The Scenes workspace's tab strip reads
  `characters.title`, `items.title`, and `locations.title` rather than keeping its own copies of
  "Characters", "Items", and "Locations".
- **A modal's own labels are named.** A form built with only a `scope:` has no model to read
  `human_attribute_name` from, so its labels are explicit keys; see below.

## The rule that is easiest to break

**A constant holds an I18n key, never a translated string.** A hash or a `freeze`d constant built at
class-load time resolves `t()` once, in whatever locale happened to load the class first, and every
later request renders that one language. `TagsHelper::UNIVERSE_TAG_METADATA` stores
`title_key:`/`description_key:` and `tag_workspace_base` resolves them per request; the same rule
governs `Search::Scope`'s option labels. A confirmation that the tree calls per record is stored as a
key and wrapped in a lambda at read time, not as a lambda that calls `t()` inside a constant.

`ModalFields` is the clearest case, because the string has to leave the server. `PHOTO_FIELD` is a
frozen constant whose label is printed by a modal the **browser** builds from the serialized
descriptors, so the constant stores `label_key:` and `ModalFields#modal_field` resolves it per
request. `SceneElementsHelper::KIND_LABEL_KEYS` and `KIND_DESCRIPTION_KEYS` are the same case: the kind
*descriptions* are serialized into `data-scene-element-form-descriptions-value` and printed by a
controller that swaps them when the Element type changes, so they cross the boundary already
translated — and they stay **keyed by the `kind` value** (`narration`, `dialogue`), because that is
what the browser matches on. The keys are data and the prose is the chrome. Two rules follow from
`ModalFields`:

- **A `freeze`d constant's lambdas capture the module, not the view.** A constant cannot hold
  `-> { universe_characters_path }`: the route helper does not exist there, and the failure is
  `undefined local variable or method … for module TagsHelper` at render time. Store the helper's
  *name* and `public_send` it, exactly as `UNIVERSE_TAG_METADATA` stores `model_param`.
- **`label_key` is how the label is found, so it is not part of the contract.** `modal_field` drops it
  on the way out; leaving it in the serialized JSON publishes a key nothing renders.

## Sentences are not nouns

Three shapes of English copy need a decision before a second language can be written, and all three
are enforced by reading the rendered page rather than by the key set.

- **The determiner belongs to the sentence.** `shared.error_summary.heading` ends in
  `"… prevented this %{subject} …"` in English, so an English `subject` is a bare noun
  (`relation`, `access grant`). Spanish has no determiner to supply one, so the Spanish sentence
  carries none and the Spanish `subject` is the whole phrase (`esta relación`, `este acceso`).
  Passing a bare noun to both renders `2 errores impidieron guardar este relación`.
- **A slot that takes one noun takes the singular.** `shared.detail_section.empty_title` is
  `"%{determiner} %{label} carries this tag"` with `label` resolved at `count: 1`. A plural cannot
  follow that verb in either language, so the earlier `"No characters carry…"` / `"Ningún personajes
  lleva…"` pair was ungrammatical in both.
- **A determiner a language agrees in gender is its own interpolation.** That key therefore takes a
  `determiner` from `shared.detail_section.determiners.none_masculine` (`"No"` / `"Ningún"`) or
  `…none_feminine` (`"No"` / `"Ninguna"`) as well as a `label`, and the caller states which beside its
  own noun — a locale cannot derive *"una sección"* from the word `sección` any more than it can derive
  its plural. The two **Section** and **Scene** record pages pass the feminine form and read *"Ninguna
  sección lleva esta etiqueta"* while the six Universe Bible record pages keep the masculine one. The
  two English entries are identical because English has no such agreement.

A **value that travels in a URL is not translated**, and neither is one that travels in a form
field. `SceneFilter::UNGROUPED`, a search scope's `value`, an `access_level` option, an `event_id`
in a `<select>`, and a `model_param` are all data the browser or the database stores; only the label
beside them is a key.

## A link inside a sentence

A sentence that carries a link is an `_html` key, and the link is the interpolation, not a fragment
the template splices into the frame: `"Change them from the %{editor}."` decides where the link sits,
where `t("…", editor: link_to(...))` puts it there. Rails escapes every interpolation of an `_html`
key (`ActiveSupport::HtmlSafeTranslation`) while leaving an already-safe value such as a `link_to`
result alone, so author data interpolated beside a link cannot inject markup.

The link's **text** stays a key of its own. `scenes.show.facts.editor_link` is `"scene editor"` while
`tags_hint_editor_html` is the sentence that carries it, because a translator choosing where the link
goes still has to know what it is called. The same split holds for `tags_hint_workspace_html`.

A template that assembled an English frame out of translated fragments — `" — see the"` + the link +
`". Several scenes can depict the same event."` — is rewritten as one sentence rather than three keys:
the fragments cannot be reordered, so three keys would mean three English sentences.

## A value object that is not a view

`SectionPaths#ungrouped_label` and `SceneFilter`'s discarded-value messages are built in models and
helpers that do not include the view's `translate` helper, so they call `I18n.t` against the request's
`I18n.locale` — the same call `Event`'s own `errors.add` messages make. A model-level `errors.add`
message is a key for the same reason: the Scene editor's error summary reads `Scene`'s own messages,
so an English literal there would render English inside an otherwise translated page, and each message
starts lowercase because it is the tail of `errors.format`.

`SceneFilter` translates its discarded values where it drops them rather than storing keys, because the
controller only has to join them with `to_sentence` — and it must join them *after* translation, or a
Spanish sentence would be assembled with English connectors.

## A label a `form_with scope:` cannot resolve

A form built with a **model** resolves `form.label :name` through
`activerecord.attributes.<model>.name`. A modal built with `form_with scope: :character, url: …` has
no model, so Rails falls back to `helpers.label.…` and then to a humanized English column name, and a
Spanish modal reads "Name" beside a Spanish error about `name`. A workspace's modal therefore names
its own labels (`characters.form.name`), while the `activerecord.attributes` entry for the same
column is what the **error message** reads. The two are expected to agree; they are separate keys
because two different call sites read them.

`Events` names `form.title` explicitly even though `activerecord.attributes.event.title` exists, for
the same reason.

## Dead keys

A `blank:` copy that can never be reached is a translation nothing renders, and it is worse than a
missing one because a reviewer cannot tell it apart from a real state. Two were removed rather than
translated: `events.show.facts.title_blank` (the value is `title.presence || display_string`, and
`display_string` always answers — at worst `"Event #12"`) and `tags.show.color_blank` (`bgcolor` is
`NOT NULL` with a default). Before adding a blank state, check what the value actually is.

## Rails' own strings

- **A `form.submit` label is named explicitly.** Rails' default label comes from `helpers.submit.*`,
  which is English only, so a full-page form passes its own label (`universes.form.submit_create`,
  `stories.form.submit_update`) rather than inheriting one.
- **An attribute name a form or an error message renders is named too.** Rails reads
  `human_attribute_name` from `activerecord.attributes.<model>.<column>`, so a Spanish page otherwise
  reads "Name" beside a Spanish error message.
- Rails defines `errors.*`, `datetime.distance_in_words.*`, and `support.array.*` in English only. The
  Spanish subset this application reaches is in `es.yml` and is checked against the real Rails key
  set, so it cannot drift into translating something the framework never asks for.

## Known gap

A **client-side** string is not a `t()` call: a Stimulus controller receives it from the server as a
Stimulus value or a rendered JSON blob. A hardcoded English string in `app/javascript` is a known
gap, not a pattern to copy. The field labels the taxonomy tree's modal is built from are **not** in
this gap: `ModalFields` resolves them server-side and ships them inside the serialized descriptors.

A model-level **label that doubles as a search document's title** is also a known gap, and it is not
one a translation can close. `Event#display_string`, `Relation#display_string`, and
`Ownership#display_string` are declared as their models' `searchable title:`, so the string is stored
in a **language-independent** index and read straight back into a result row. Translating it in the
model would put one locale's chrome in that index and show it to a reader in another language.
`Event#display_string`'s three relationship phrases (`"before X"`, `"after X"`, `"same time as X"`)
and `Ownership#display_string`'s `"X owns Y"` are therefore still English. Resolving them at read
time — which is the rule above — needs a decision that belongs with the slice that owns the
model-level labels, not with a page.
