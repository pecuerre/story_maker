What this comparison tests

Item 81 asks whether Scene Details should carry labelled links to its neighbours. Today the page states its narrative position and offers All scenes, but it has no previous or next link, so reading a story end to end means returning to the list after every scene. The proposal is one narrative rail above the Elements and one below the drafting contract. It is a static mock of the real page markup, not a running Rails page; the application view is untouched. The scene's prose and identity values are illustrative, and only the scene identity and the rail's boundaries change between states. The direction was accepted on 2026-11-19 and is now implemented; the one-scene Story renders only the top rail so its message is not repeated.

Recommended

Both rails, always the whole story. The top rail is reachable on arrival; the bottom rail catches a reader who has finished the page. Previous and next mean the adjacent scenes in Scene#position, never the adjacent rows of a filtered list.

Each link names its direction, the neighbouring title, and the whole-story position (Scene 6 of 24 · Chapter one). At a boundary the missing side becomes plain text — Start of the story or End of the story — rather than a disabled or dead link. A single-scene Story says so once instead of drawing two empty halves.

A filtered list stays a filtered list

The proposal does not carry the filter into Scene Details. A filter narrows the list; it is a view of the Story, not a second narrative order. If the rail walked only matching rows, Next would mean “next scene that still matches”, silently skipping scenes the reader cannot reach, and the last match would need a third action to continue. Instead every rail meta names the whole sequence, and the header already says Scene 7 of 24, so a reader arriving from four matches can see that the rail is the Story. The filtered list itself is one browser Back away; All scenes remains the canonical whole list. Use the Arrival: Filtered list control to see the same page and rail with that origin recorded in the address bar.

Preserved in both layouts

  • The title, the Story eyebrow, the position sentence, the Edit scene primary action, All scenes, and the workspace tabs are unchanged.
  • The Elements stay the first substantive block, above the identity card and the drafting contract.
  • Every access level sees the rail, because following the Story is reading; it is not a write control and does not appear only for writers.
  • The rail is a <nav> landmark with normal anchors, visible labels, and a visible focus ring. It never depends on hover, a menu, or colour.
  • The centre position is text, not a control, and each link's accessible name carries its direction and the neighbour's position and title. All scenes stays in the header rather than being repeated in the rail.
  • Boundary states are explicit text. No control is rendered as a disabled button, so it cannot look like an action that might work later.
  • The page still has one editor and one write path; the rail never changes grouping, status, or position.

What the placement changes

Top puts the next scene within reach before the long identity list; Bottom closes the page like the end of a chapter, after the drafting contract; Both is the proposal, at the cost of a second rail. At phone width the rail stops being three columns: the position sits on its own line above stacked previous and next cards, so long titles are not squeezed into half a phone.
